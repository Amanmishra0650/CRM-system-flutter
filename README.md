# Bike Rescue - Flutter + API + PostgreSQL

This repository is a **development implementation** of the Bike Rescue blueprint. It contains one role-aware Flutter app (rider, mechanic and admin views), a Node/Express TypeScript API and a PostgreSQL/PostGIS schema. It is **not production ready**: real OTP delivery, payment gateway order creation, live tracking, media uploads, towing and native platform builds are outstanding.

## Structure

- `flutter_app/`: Flutter UI with light orange theme and a built-in two-wheeler logo; role-based screens.
- `api/src/`: authenticated API and rescue domain rules.
- `api/sql/001_initial.sql`: PostgreSQL/PostGIS schema.
- `api/test/`: domain tests.
- `docker-compose.yml`: local PostGIS database with a persistent Docker volume.
- `docs/`: limitations and follow-up checklist.

## Run on Windows PowerShell

Install Flutter SDK, Android Studio, Node.js 20+ and Docker Desktop. In the repository root:

```powershell
docker compose up -d
cd api
Copy-Item .env.example .env
# Edit api/.env: replace JWT_SECRET with a long random value. Local database URL is already shown in the example.
npm install
npm run migrate
npm run check
npm test
npm run dev
```

Open another PowerShell terminal:

```powershell
cd flutter_app
flutter create --platforms=android,ios,web .
flutter pub get
flutter analyze
flutter run --dart-define=API_URL=http://10.0.2.2:4000/api/v1
```

`10.0.2.2` is for the Android emulator. For a real phone, pass your PC's LAN IP. For Windows desktop, use `http://localhost:4000/api/v1`. Flutter platform directories are generated by `flutter create`; generate and commit them on a machine with the Flutter SDK. The API must be reachable from the device. Android local cleartext development may require a debug-only network-security setting; use HTTPS in production.

The development OTP is printed in the API terminal and never returned to the app. OTP sign-in deliberately fails outside `NODE_ENV=development` with `OTP_PROVIDER=console`. Set these in `api/.env` for local development; integrate a real provider before deployment. For Flutter web, set CORS_ORIGIN to its exact local web origin. For an initial admin, configure `BOOTSTRAP_ADMIN_PHONE` and `BOOTSTRAP_ADMIN_SECRET`, call `POST /api/v1/admin/bootstrap` with `x-bootstrap-secret`, then remove those environment variables. The admin signs in through the same OTP flow.

## Supported API flow

1. Register rider and mechanic with OTP; admin verifies mechanic.
2. Rider adds vehicle and submits SOS with an idempotency key.
3. Verified, online mechanics within radius see eligible requests and submit ETA/charge offers.
4. Rider selects one offer. Database transaction prevents conflicting assignment.
5. Mechanic advances job, submits itemized estimate; rider approves or declines.
6. Payment record remains pending until a signed provider webhook is received. Invoice is available only after completed, verified payment.

## Known gaps before live launch

- Flutter SDK was unavailable in the authoring workspace, so `flutter analyze`, device launch and platform build are not verified here.
- OTP provider, gateway order creation, live sockets/tracking, map confirmation, media storage, invoice PDF, detailed verification documents, cancellation policy and real-world integration tests need implementation.
- Payment webhook is an integration skeleton: adapt its payload, signature format and reconciliation to the chosen provider; never expose the webhook secret to Flutter.
- Configure production HTTPS, persistent WebSocket hosting, backups, monitoring, privacy retention and appropriate operations policies.
